Selected work

Pexiscale

Multi-tenant business platform, live at pexiscale.com

Customers, catalog, inventory, quotes and orders for small and medium businesses, on one platform where each company's data stays its own. I design and build it.

  • PostgreSQL is the source of commercial truth. Price, stock and order state are decided on the server. The AI interprets a request and suggests; the commercial domain decides.
  • Tenant isolation lives in the database. Every tenant-owned row carries an organization id and is protected by row-level security, not by filtering in the client.
  • Scripted CI guards fail the build when the legacy, deploy or marketing boundaries regress, and when secrets are committed.
Evidence
Pull requests into the main branch go through a CI gate that includes boundary and secret-scanning guards.
Still open
Not every implemented capability is switched on in production. Some depend on provider approval and rollout, and I list a capability as live only when it is.

Lume

Research on memory-efficient data and computation, public at github.com/guilhermehrcst/lume. Formerly named PXIR.

An open project asking whether software and data can be represented with less memory and less data movement without losing correctness. The first rule: no optimization claim without a measurement.

  • A verifier is the only way to obtain an executable program. The type system makes running unverified IR impossible to write.
  • Each milestone states a hypothesis, the measurement and the outcome, including the hypotheses that were falsified.
  • C++20 core with a C baseline. CI builds on Linux, macOS and Windows, and runs the tests under AddressSanitizer and UBSan.
Evidence
Code, benchmarks and a write-up per milestone are public. In one benchmark, reusing a dead buffer cut page faults from 2,016 to 0 per call (1M elements, measured).
Still open
Early research. No production or universal performance claims; results hold for the stated workloads and machines.

Paulex

Commerce backend for my retail brand. The repository is private.

The order and payment core of the Paulex online store. Orders are created only on the server, and a retried request never creates a second order.

  • One database function creates orders. The client sends only product, variant and quantity; the server decides the price.
  • Stock reservation takes row locks in a fixed order, so concurrent orders can't oversell or deadlock each other.
  • The payment webhook verifies the signature, re-reads the payment from the provider, and compares order, amount and currency. If it hasn't applied the effect, it answers with an error status so the provider retries.
Evidence
SQL tests run against a real Postgres, including concurrent sessions competing for the same stock. Security assertions are tested by breaking them on purpose and checking that the test fails.
Still open
The code is private, so this is a description you can't run. I'm happy to walk through it.
